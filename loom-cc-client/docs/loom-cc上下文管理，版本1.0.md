# Loom CC 上下文管理功能说明，版本 1.0

## 1. 文档定位

这是一份面向用户、产品、设计和测试的功能说明文档，不是技术实现文档。

本文说明 Loom CC 在“上下文管理”上做了什么、用户能看到什么、每个流程如何运转，以及 Loom 相比命令行工具在上下文管理上的产品化优势。

这里的“上下文”可以简单理解为：AI 在回答你之前，能够参考和使用的信息。

这些信息包括：

- 你当前输入的问题。
- 当前会话里最近的对话。
- 当前项目的说明、文件、目录和工作区信息。
- 你上传的图片、PDF、文本文件等附件。
- 已确认的长期记忆。
- 项目内的 skills、规则、工作流和工具能力。
- 之前压缩后的摘要。
- 工具执行结果和任务状态。

上下文管理的目标不是让 AI 看到越多越好，而是让 AI 看到“当前任务真正需要的信息”。

## 2. 为什么需要上下文管理

如果没有上下文管理，长时间使用 AI 做项目会出现几个典型问题。

| 问题 | 用户感受 | 后果 |
| --- | --- | --- |
| 对话越来越长 | AI 回复变慢，成本变高 | 每次回答都携带大量历史信息 |
| 重要信息被淹没 | AI 忘记关键要求 | 需要反复提醒 |
| 项目资料太多 | 不知道 AI 到底看了什么 | 回答不稳定 |
| 附件过大 | 上传后卡顿或失败 | 上下文被单个文件撑爆 |
| 工具输出太长 | 一次命令输出占满上下文 | 后续对话质量下降 |
| 记忆无限增加 | AI 被旧信息干扰 | 越用越乱 |
| 压缩不可见 | 不知道什么时候压缩了 | 用户缺少控制感 |

Loom CC 的上下文管理就是为了解决这些问题。

核心原则是：

让 AI 持续理解项目，但不要把所有信息都无脑塞进每一次对话。

## 3. Loom CC 的上下文管理目标

Loom CC 的上下文管理围绕五个目标设计。

### 3.1 可持续长对话

用户可以在一个项目里持续多轮对话，不需要频繁重新开会话，也不需要手动复制历史内容。

当会话变长时，Loom 提供压缩能力，把旧对话整理成摘要，让后续对话继续进行。

### 3.2 跨会话记忆

项目里的关键事实、决策、偏好、反馈和复盘，不应该只停留在某一个 session 里。

Loom 不再把“记忆”简单理解为一堆待确认文本，而是采用四层记忆结构：

- L0 事实记录：确定发生过的消息、事件和操作，只增不改。
- L1 近期观察：本次或近期会话中的状态信号，短期有效。
- L2 语义记忆：跨多次观察后形成的稳定规律、偏好、规则和风险。
- L3 项目档案：当前项目的阶段性理解摘要，用于后续上下文注入。

用户不需要频繁管理这些层级。普通对话默认只走低成本记录和确定性闸门；只有高影响、冲突或低置信的重要事项才需要用户确认。

### 3.3 跨项目可控共享

有些记忆适合全局共享，例如用户偏好的输出语言、写作风格、常用格式。

有些记忆只能留在当前项目，例如客户资料、项目决策、业务规则。

Loom 将记忆分为全局记忆和项目记忆，避免不同项目之间互相污染。

### 3.4 上下文可见

用户不应该完全猜测 AI 这次到底用了多少上下文。

Loom 会在 AI 回复后展示输入 token、输出 token、上下文使用情况、压缩边界和记忆状态，让用户知道当前会话是否健康。

### 3.5 上下文可控

当上下文过长、附件过大、记忆重复、工具输出过多时，Loom 不应该只是继续堆信息。

Loom 会通过压缩、提醒、裁剪、候选确认、分层记忆等方式，让上下文保持可控。

## 4. 功能总览

| 功能 | 用户看到什么 | 解决什么问题 |
| --- | --- | --- |
| 会话上下文延续 | 在同一个 session 中持续聊天 | 不用每次重新说明背景 |
| 项目上下文 | AI 理解当前项目和工作区 | 不同项目之间互不混乱 |
| Memory / Evolution Center | 查看项目理解、稳定规律、近期观察和待处理事项 | 重要信息跨 session 保留并持续修正 |
| 四层记忆 | L0 事实、L1 观察、L2 规律、L3 档案 | 避免把事实、观察和长期认知混在一起 |
| 三道闸门 | 价值过滤、置信过滤、晋升/去重过滤 | 控制什么该记、什么该丢、什么该升级 |
| 低 token 进化 | 普通对话零新增 LLM，批处理晋升 | 避免每轮都为 memory 单独调用模型 |
| 手动压缩 `/compact` | 显示压缩进度、分割线和摘要 | 长对话继续推进 |
| 自动压缩 | 上下文过长时自动整理 | 降低长会话失控风险 |
| Token 展示 | 每次 AI 回复下方显示 In / Out | 用户知道本次消耗 |
| 输入 Token 分类 | 鼠标悬浮查看输入组成分类 | 用户理解输入来自哪里 |
| 附件大小治理 | 大附件提醒或限制 | 防止单个附件撑爆上下文 |
| 工具结果瘦身 | 长输出展示和上下文分开处理 | 防止工具输出污染后续对话 |
| Prompt 结构预览 | 高级模式下查看上下文结构 | 便于排查 AI 为什么这样回答 |
| 压缩分割线 | 聊天流中出现明确边界 | 用户知道上下文发生过整理 |
| 项目统计 | 项目内查看用量与状态 | 了解项目级使用情况 |

## 5. 用户能感知到的上下文组成

一次 AI 回复并不是只看用户刚刚输入的一句话。

Loom 会把输入上下文按用户能理解的方式分成以下几类。

| 分类 | 含义 | 用户是否需要手动处理 |
| --- | --- | --- |
| 系统与运行环境 | AI 需要遵守的基础规则和运行能力 | 不需要 |
| 项目与工作区 | 当前项目、目录、工作区和项目说明 | 通常不需要 |
| 会话历史 | 当前 session 中的历史对话 | 不需要 |
| Compact 摘要 | 压缩后保留的历史摘要 | 必要时可查看 |
| Memory 记忆 | L3 项目档案、L2 相关规律、最近 L1 观察和必要规则 | 通常不需要 |
| Skills / Agents / 工具 | 当前项目可用的专业能力和工具 | 可以配置 |
| 工具权限 | 当前允许 AI 做什么操作 | 可以配置 |
| 附件 | 用户上传的图片、PDF、文本等 | 用户主动上传 |
| 当前输入 | 用户本轮输入的问题或任务 | 用户输入 |

这些分类会在输入 token 说明中展示，帮助用户理解“本次输入为什么会这么大”。

## 6. 正常聊天流程

### 6.1 用户发送一条消息

用户在当前项目或当前 session 中输入内容并发送。

Loom 会自动准备本轮上下文：

1. 识别当前项目。
2. 识别当前 session。
3. 带上必要的会话历史。
4. 带上当前项目的基础信息。
5. 检查是否有附件。
6. 检查是否有可用的记忆。
7. 检查是否有压缩后的摘要。
8. 组合成本轮 AI 可以理解的上下文。
9. 开始生成回复。

用户不需要手动选择这些信息。

### 6.2 AI 回复过程中

用户会在聊天界面看到 AI 流式输出。

如果 AI 调用了工具、更新任务、读取文件或产生中间状态，Loom 会在界面中展示对应状态。

如果本轮触发了上下文压缩，Loom 会在聊天流里显示压缩相关状态。

### 6.3 AI 回复完成后

Loom 会更新以下信息：

1. 本轮输入 token。
2. 本轮输出 token。
3. 当前上下文使用情况。
4. 是否产生新的 L1 观察、L2 强化或待处理事项。
5. 是否产生新的任务状态。
6. 是否发生过压缩。
7. 是否需要刷新右侧 Memory 或 Tasks。

用户看到的是一次完整的 AI 回复，但 Loom 在背后会同步维护上下文状态。

## 7. Token 展示功能

### 7.1 每次回复显示真实 In / Out

每次 AI 回复完成后，assistant 消息下方会展示：

- `In`：本次输入 token。
- `Out`：本次输出 token。

这两个数据放在消息底部信息区，和耗时等信息处于同一层级。

这样用户可以快速判断：

- 本轮是不是输入过大。
- 本轮是不是输出过长。
- 哪些任务比较消耗上下文。

### 7.2 输入 Token 组成分类

当用户将鼠标悬浮到输入 token 区域时，Loom 会展示“输入Token组成分类”。

该分类不是给用户展示复杂技术细节，而是解释输入大致由哪些部分构成。

分类包括：

| 序号 | 分类 | 说明 |
| --- | --- | --- |
| 1 | 系统与运行环境 | AI 运行时需要遵守的基础规则和能力说明 |
| 2 | 项目与工作区上下文 | 当前 project、workspace、目录和项目相关信息 |
| 3 | 会话历史 | 当前 session 中为了延续对话而携带的历史内容 |
| 4 | Compact 摘要 | 压缩旧对话后保留的摘要 |
| 5 | Memory 记忆 | L3 项目档案、L2 相关规律、最近 L1 观察和必要规则 |
| 6 | Skills / Agents / 工具 | 当前可用的专业能力和工具说明 |
| 7 | 工具权限 | 当前允许 AI 执行哪些操作 |
| 8 | 附件 | 用户上传的图片、PDF、文本等 |
| 9 | 当前用户输入 | 用户本轮输入的问题或任务 |

这个功能的目的不是让普通用户理解 token 细节，而是让用户知道：输入 token 并不只来自自己刚输入的那句话。

### 7.3 Memory 的 token 控制

Memory 不是越多越好。

Loom 对 memory 的 token 控制采用固定预算和分层注入：

- 不把全部 memory 文件塞进每次输入。
- 不把完整证据链塞进 prompt，只引用 evidence id。
- 优先注入 L3 项目档案。
- 再按相关性和强度选择少量 L2 语义记忆和 active project rules。
- 最后只带最近少量 L1 观察。

这样输入 token 不会随着历史数据线性增长。

Memory 写入也要控制模型调用：

- 普通 `after_message` 不再单独调用 LLM 做 memory 抽取。
- L0/L1 通过确定性规则、阈值和状态机写入。
- L1 到 L2 的晋升攒批处理。
- 只有语义模糊、冲突、边界不清的情况才调用 skill。

这保证了“自我进化”不会变成每轮对话额外消耗一次模型调用。

## 8. 上下文压缩功能

### 8.1 什么是压缩

压缩可以理解为：把前面较长的对话整理成一份更短的摘要，让后续对话继续使用这份摘要，而不是每次都携带完整旧历史。

压缩不是删除聊天记录。

聊天界面仍然可以看到历史消息，但 AI 后续参考的内容会更加精简。

### 8.2 为什么需要压缩

长对话继续累积会带来几个问题：

- AI 回复变慢。
- 消耗 token 增加。
- 重要信息被大量旧内容淹没。
- 可能达到上下文上限。
- 后续回答开始不稳定。

压缩的目标是保留关键事实、决策、任务进度和待办，同时减少无关细节。

### 8.3 手动 `/compact`

用户可以在聊天输入框输入：

```text
/compact
```

执行后，Loom 会进入压缩流程。

用户会看到：

1. `/compact` 命令出现在聊天输入下方或消息流中。
2. 出现与压缩动作匹配的进度动画。
3. 压缩完成后，进度动画消失。
4. 聊天界面出现明显的压缩分割线。
5. 分割线附近展示压缩摘要。
6. 后续对话继续基于压缩后的上下文推进。

### 8.4 压缩分割线

压缩完成后，聊天界面会出现一条明确的分割线。

这条分割线告诉用户：

- 从这里开始，上下文已经被整理过。
- 前面的长对话没有从界面删除。
- 后续 AI 会基于压缩后的状态继续工作。

分割线的作用是降低用户的不确定感。

用户不需要猜测“是不是压缩过”，也不需要去日志里找。

### 8.5 压缩摘要

压缩摘要用于告诉用户本次压缩保留了哪些核心内容。

摘要应该包含：

- 当前任务目标。
- 已完成事项。
- 重要事实。
- 关键决策。
- 未完成待办。
- 用户偏好或约束。
- 后续继续时需要注意的事项。

摘要不应该包含大量无意义寒暄，也不应该把所有历史消息重新复述一遍。

### 8.6 自动压缩

当上下文接近较高使用比例时，Loom 支持自动触发压缩或配合底层能力进行自动压缩。

用户不需要手动计算上下文是否快满。

自动压缩发生后，Loom 仍然会在界面中展示压缩边界，让用户知道发生了什么。

自动压缩的目标是：

- 尽量避免长会话突然不可继续。
- 尽量减少用户手动管理成本。
- 保留长任务连续性。

### 8.7 压缩后的继续对话

压缩完成后，用户可以继续正常提问。

用户不需要：

- 重新创建 session。
- 手动复制摘要。
- 手动告诉 AI “这是前面的总结”。
- 重新上传项目背景。

Loom 会把压缩后的状态作为后续上下文的一部分。

## 9. Memory 记忆功能

### 9.1 事实、观察和记忆的区别

会话历史是当前 session 内的对话记录。

Memory 不是简单的历史摘录。Loom 会把“发生过什么”和“系统理解了什么”分开处理。

区别如下：

| 类型 | 生命周期 | 适合保存什么 |
| --- | --- | --- |
| 会话历史 | 当前 session | 本轮讨论、临时上下文、过程信息 |
| L0 事实记录 | 长期留痕，只增不改 | 消息、操作、候选来源、确认/拒绝记录 |
| L1 近期观察 | 短期有效，可被晋升或归档 | 本次对话暴露出的偏好、风险、纠正、状态信号 |
| L2 语义记忆 | 当前项目长期有效，但会增强、衰减、过期 | 稳定规律、项目规则、重复反馈、复盘结论 |
| L3 项目档案 | 阶段性摘要，低频重算 | 当前项目理解、稳定规则、近期风险、废弃认知 |
| 全局记忆 | 所有项目可用 | 用户偏好、通用输出格式、常用工作方式 |

关键区别是：

- L0 回答“发生了什么”。
- L1 回答“这次观察到什么”。
- L2 回答“这个项目长期看有什么规律”。
- L3 回答“当前项目整体应该如何理解”。

AI 越来越懂项目，靠的是 L2 和 L3 的持续修正，而不是把 L0 无限堆进上下文。

### 9.2 三道闸门

每条信息进入记忆前要经过三道闸门。

第一道是价值过滤。

Loom 会判断这条信息下次处理这个项目时是否还可能有用。寒暄、一次性任务细节、纯过程推理、L0 已能完整表达的事实，不进入长期记忆。

第二道是置信过滤。

高置信、低风险的信息可以自动写入 L1 或强化 L2。中等置信或高影响事项进入待处理区。低置信信息只保留 L0 留痕，不影响后续上下文。

第三道是晋升/去重过滤。

L1 不会直接变成项目规则。只有当同一方向被多次独立证据印证，或者用户明确表达长期规则时，才会晋升为 L2 语义记忆或项目规则。晋升前先做确定性去重，只有语义模糊的边界 case 才调用 skill。

### 9.3 为什么用户不需要频繁确认

早期设计是：

```text
AI 自动提炼
  ↓
待确认记忆
  ↓
用户逐条确认
  ↓
正式记忆
```

这个流程安全，但用户操作过多，不符合“自我进化”的产品目标。

新的流程是：

```text
普通对话
  ↓
L0 事实记录 + cheap gate
  ↓
有价值信号进入 L1 观察
  ↓
批量晋升 / 去重 / 衰减
  ↓
形成或强化 L2 语义记忆 / 项目规则
  ↓
低频重算 L3 项目档案
  ↓
下一轮按需注入
```

用户只在以下情况参与：

- 规则影响范围大。
- 规则可能冲突。
- 置信度不足但影响较高。
- 用户主动要求确认、编辑或否决。
- 系统准备废弃重要长期认知。

普通记忆不应该让用户像处理 inbox 一样逐条管理。

### 9.4 全局记忆

全局记忆适合保存跨项目都适用的信息。

例如：

- 用户希望默认用中文回答。
- 用户喜欢结构化输出。
- 用户偏好先给结论再给解释。
- 用户常用的文档格式。
- 用户希望代码修改前先说明影响。

全局记忆不适合保存某个客户、某个项目、某个私有业务的数据。

### 9.5 项目记忆

项目记忆只在当前项目内生效。

适合保存：

- 当前项目目标。
- 当前项目里的关键业务规则。
- 已确认的产品决策。
- 用户对某次输出的反馈。
- 复盘结论。
- 已经踩过的坑。
- 项目专属术语。
- 项目专属输出格式。

项目记忆的价值在于：换一个 session 后，AI 仍然能理解这个项目长期积累下来的背景。

### 9.6 低 token 写入策略

Memory 的成本控制原则是：

- 能用确定性规则就不调用 LLM。
- 普通 `after_message` 不单独跑 memory extractor。
- L0/L1 写入走规则、阈值和状态机。
- 候选信息尽量搭车已有主任务或 skill 输出。
- L1 到 L2 的晋升批量处理，不每条观察实时调用模型。
- 先用知识点、标签、关键词、来源和状态做确定性去重。
- 只有边界模糊 case 才交给 `memory-curator`、`rule-promoter`、`rule-auditor` 等 skill。

单次普通对话的默认路径应接近 0 次新增 LLM 调用。

### 9.7 L1 到 L2 的晋升流程

Loom 的晋升流程如下：

```text
普通对话 / compact / manual / periodic
  ↓
记录 L0 facts
  ↓
cheap gate 识别价值和置信度
  ↓
写入 L1 observation
  ↓
攒批触发 promotion
  ↓
确定性去重与合并
  ↓
重复证据强化已有 L2，或创建新的 L2
  ↓
更新 L3 project dossier
```

触发 promotion 的典型时机：

- `/compact` 后。
- 用户手动刷新项目理解。
- 周期性 evolution audit。
- L1 观察攒够数量。
- 出现明确的长期规则信号。

### 9.8 显式“记住”流程

用户也可以直接告诉 Loom：

```text
请记住：以后这个项目里的脚本输出都要包含执行步骤和验证方式。
```

这类明确要求会被优先识别为记忆意图。

如果用户说的是：

```text
请记住我上面的提问。
```

Loom 不应该只记住“我上面的提问”这几个字，而应该回看前面的对话，提取真正需要记住的内容。

这是记忆提炼质量的重要标准。

显式“记住”不是要求用户管理所有 memory，而是给用户一个主动写入的入口。

### 9.9 记忆去重和 negative prior

长期使用中，同一条记忆可能被多次提取。

Loom 需要减少重复观察、重复语义记忆和重复待处理事项。

去重逻辑应该覆盖：

- 内容完全相同。
- 表达不同但含义相近。
- 同一事实在多轮对话中反复出现。
- 已经确认过的记忆再次出现。
- 已忽略过的候选再次出现。
- 用户明确否决过的方向再次出现。

这样可以避免右侧 Memory 被大量重复内容污染，也避免 L2 长期认知膨胀。

如果用户否决某条规则或认知，Loom 会记录 negative prior。

negative prior 的作用是：

- 降低同方向候选再次出现的概率。
- 提高未来同方向晋升门槛。
- 避免系统反复提出用户已经判断过的错误理解。

### 9.10 记忆不会无限注入

记忆越多，并不代表每次都应该全部给 AI。

Loom 的记忆管理目标是：

- 记忆可以长期保存。
- 使用时只选择当前任务相关的部分。
- 不把所有记忆无脑塞进每一次输入。
- 尽量把本次记忆上下文控制在轻量范围内。

实际注入策略是固定预算：

- L3 项目档案摘要。
- L2 active 语义记忆和项目规则 top-K。
- 最近少量 L1 观察。
- 证据只引用 id，不把完整证据链灌入上下文。

这样既保留长期项目知识，又避免上下文被记忆撑爆。

### 9.11 衰减、过期和归档

长期记忆不是永久正确。

项目会变化，用户会改变偏好，过去的问题也可能已经解决。

所以 L2 语义记忆和项目规则需要生命周期：

- 新证据印证时，`strength` 和 `occurrences` 上升。
- 长期没有新证据时，`stale_score` 上升，注入权重下降。
- 超过过期阈值仍无印证时，进入 stale 或 archived。
- 用户否决时，归档对应认知，并写入 negative prior。

这可以避免 AI 永远盯着已经过时的问题。

## 10. 项目上下文管理

### 10.1 项目是上下文的边界

Loom 以项目作为重要的上下文边界。

不同项目之间应该有独立的：

- session。
- 文件目录。
- 项目说明。
- 项目记忆。
- 任务状态。
- skills 使用习惯。
- 统计信息。

这样可以避免 A 项目的业务规则影响 B 项目。

### 10.2 没有 session 时的项目状态

当项目还没有 session 时，Loom 不应该让用户看到一个空白或错误状态。

当前设计是：

- 进入项目后显示项目统计页面。
- 页面下方仍然可以直接输入。
- 用户输入第一条消息后自动进入新的 session。

这样可以降低“先创建会话再提问”的操作成本。

### 10.3 项目统计页面

项目统计页面用于展示当前项目的整体状态。

它不是全局统计，而是当前项目维度的统计。

适合展示：

- 当前项目 session 数。
- 当前项目消息数。
- 当前项目 token 使用情况。
- 当前项目任务状态。
- 当前项目 memory 状态。

用户进入项目时可以先看到项目状态，再决定下一步操作。

## 11. 附件上下文治理

### 11.1 为什么附件需要治理

附件很容易让上下文失控。

例如：

- 一个 PDF 可能非常长。
- 一个代码文件可能包含大量无关内容。
- 一个图片可能需要视觉理解。
- 一个压缩包可能无法直接进入上下文。
- 多个附件叠加后会显著增加输入成本。

所以 Loom 不能把所有附件都简单塞给 AI。

### 11.2 附件大小提醒

当附件超过 20MB 时，Loom 应该给出明确提醒。

提醒的目标是：

- 告诉用户文件过大。
- 避免直接发送导致失败或卡顿。
- 引导用户选择更合适的处理方式。

可选处理方式包括：

- 重新选择更小的文件。
- 只上传关键页面或关键截图。
- 先生成摘要。
- 将大文件转为可检索资料。
- 按需引用文件内容。

### 11.3 小附件

小附件可以直接进入当前对话。

适合：

- 单张截图。
- 小文本。
- 简短 PDF。
- 少量代码片段。

用户体验应该接近“上传后直接问”。

### 11.4 中等附件

中等附件不一定适合完整进入上下文。

Loom 可以采取：

- 提取关键文本。
- 限制最大读取长度。
- 优先读取开头、目录、标题和用户指定部分。
- 必要时提示用户说明关注点。

### 11.5 大附件

大附件不应该直接全部进入上下文。

更合理的方式是：

- 先提醒。
- 再预览。
- 再摘要。
- 再按需引用。

未来可以支持附件索引，让 AI 在需要时检索具体片段，而不是每次都带上完整文件。

## 12. 工具结果瘦身

### 12.1 为什么工具结果需要瘦身

AI 调用工具后可能产生很长的结果。

例如：

- 终端命令输出几千行。
- 文件搜索命中大量结果。
- 构建日志非常长。
- 测试失败堆栈很长。
- 读取大文件返回大量内容。

如果这些结果全部进入后续上下文，会很快撑爆上下文。

### 12.2 Loom 的处理方式

Loom 需要区分两件事：

- 用户界面上是否展示。
- 后续上下文中是否继续携带。

用户界面可以保留更多可查看内容。

但后续上下文中应该只保留必要摘要、关键错误、关键文件和关键结论。

### 12.3 用户能感受到什么

用户能看到工具执行过什么、是否成功、关键输出是什么。

但 Loom 不会因为一次超长工具输出，就让后续所有 AI 回复都背负这份长输出。

这样可以让长任务更稳定。

## 13. Prompt 结构预览

### 13.1 功能定位

Prompt 结构预览是高级功能，不是普通用户每天都需要看的功能。

它用于回答一个问题：

AI 这次回答之前，大概参考了哪些类型的信息？

### 13.2 预览内容

预览应该展示结构，而不是泄露完整敏感内容。

适合展示：

- 当前输入。
- 会话历史是否携带。
- 是否有 compact 摘要。
- 是否使用 memory。
- 是否使用附件。
- 是否有项目上下文。
- 是否有 skills 或工具上下文。
- 大致 token 占比。

不适合展示：

- 完整密钥。
- 完整隐私文件。
- 大量原始工具输出。
- 未经处理的敏感内容。

### 13.3 使用场景

适合以下场景：

- 用户觉得 AI 答非所问。
- 用户怀疑 AI 没看到某个文件。
- 用户想知道为什么输入 token 很高。
- 用户调试 memory 是否生效。
- 用户调试 compact 后是否丢失信息。

## 14. 右侧 Memory 面板

### 14.1 面板目标

Memory 面板不是单纯展示文件内容，也不是审计日志浏览器。

它应该帮助用户完成三件事：

- 看懂 Loom 当前如何理解这个项目。
- 处理真正需要用户判断的高影响事项。
- 预览哪些项目理解会影响下一轮 AI。

右侧面板应该服务普通用户的判断，而不是暴露内部账本。

不应该常驻展示：

- Topic 文件列表。
- `MEMORY.md` 原文摘要。
- L0 fact records。
- evolution audit log。
- active/shadow rules 的完整内部清单。

这些信息可以保留在 API、文件或调试入口里，但不应该占用主界面。

### 14.2 面板结构

右侧 Memory 面板应保留以下区域：

| 区域 | 展示什么 | 用户操作 |
| --- | --- | --- |
| 自动进化概览 | 需处理数量、L2 规律数量、L1 观察数量、active 规则数量 | 刷新项目理解 |
| L3 Project Dossier | 当前项目理解摘要、近期风险、已废弃认知 | 查看 |
| L2 Semantic Memories | 稳定规律、强度、出现次数、是否 stale | 查看 |
| L1 Recent Observations | 最近少量有价值观察 | 查看 |
| 需要处理 | 高影响、冲突、低置信但重要的候选规则或记忆 | 确认、继续观察、废弃、编辑 |
| 注入预览 | 本轮将注入的 dossier / top-K memory / observations | 查看 |

### 14.3 需要处理区域

需要处理区域只展示真正需要用户判断的事项。

典型包括：

- 高影响项目规则。
- 可能影响全局行为的规则。
- 与已有规则冲突的候选。
- 用户明确要求记住但系统无法高置信解析的内容。
- 系统准备废弃的重要长期认知。

用户可以：

- 确认。
- 编辑后确认。
- 忽略。
- 删除。
- 继续观察。

普通 L1 观察、自动强化、低风险 shadow rule，不应该频繁打扰用户。

### 14.4 自动局部刷新

当 `/compact`、手动刷新项目理解或周期性进化产生新的 L1/L2/L3 状态变化时，右侧 Memory 面板应该自动刷新。

用户不应该手动刷新页面才能看到新的项目理解或待处理事项。

### 14.5 稳定认知区域

稳定认知不应该按文件原文展示，而应该按认知层级展示。

用户应该可以：

- 查看。
- 理解强度和是否过期。
- 看出哪些规律正在影响 AI。
- 看到哪些认知已经废弃。

这能让用户对 AI 长期记住的内容有控制权。

## 15. Tasks 与上下文

### 15.1 Tasks 为什么属于上下文

任务状态会影响 AI 后续回答。

例如：

- 哪些任务已经完成。
- 哪些任务正在进行。
- 哪些任务被阻塞。
- 用户反馈了哪些问题。
- 下一步应该做什么。

这些都属于项目持续推进的上下文。

### 15.2 自动切换 Tasks

当用户发送消息后，如果 AI 本轮产生或更新了 tasks，Loom 可以自动切换到右侧 Tasks tab。

这样用户能及时看到任务状态变化。

### 15.3 Tasks 与 session 的关系

Tasks 更适合跟随 session 或项目任务流保存。

刷新页面后不应该丢失。

如果任务是当前项目的长期工作项，后续应该支持沉淀到项目级任务视图。

## 16. 上下文健康状态

### 16.1 什么是上下文健康

上下文健康不是单纯看 token 总数。

还要看：

- 最近消息是否过长。
- 记忆是否重复。
- 附件是否过大。
- 工具结果是否过长。
- 是否已经很久没有压缩。
- 是否有大量无关历史。
- 当前任务是否还清晰。

### 16.2 健康状态提醒

Loom 可以通过轻量提示告诉用户：

- 当前上下文较健康。
- 当前对话较长，建议压缩。
- 附件较大，建议摘要。
- 需要处理的高影响事项较多，建议查看。
- 工具输出过长，已自动瘦身。

提醒应该克制，不应该打断用户工作流。

### 16.3 不再做不可靠的发送前估算

发送前估算 token 往往不准确。

原因是：最终输入可能包含工具、skills、项目配置、运行环境、历史恢复等多种内容。

所以 Loom 不应该用不准确的估算去强行阻止用户发送。

更合理的方式是：

- 回复完成后展示真实用量。
- 使用真实用量更新上下文状态。
- 在必要时给出压缩建议。
- 让自动压缩处理高风险长会话。

## 17. Loom 相比 CLI 的上下文管理优势

这里的 CLI 指命令行形态的 AI 工具。

CLI 很适合开发者直接操作，但对普通用户来说，上下文管理通常不够可见、不够可控。

Loom 的优势是把上下文管理产品化。

### 17.1 可视化

| 能力 | CLI | Loom |
| --- | --- | --- |
| 当前输入 / 输出 token | 通常不明显 | 每次 AI 回复后直接展示 |
| 上下文使用情况 | 需要用户自己判断 | 界面中展示上下文状态 |
| 压缩发生时机 | 用户不一定看得清楚 | 聊天流中显示压缩边界 |
| 压缩摘要 | 不一定产品化展示 | 分割线附近可见 |
| Memory 候选 | 通常依赖文件或手工维护 | 右侧面板可确认、编辑、忽略 |
| 项目状态 | 需要命令行和文件判断 | 项目页面可视化 |

### 17.2 更适合非工程用户

CLI 假设用户理解很多概念，例如工作目录、配置文件、上下文窗口、压缩、memory 文件。

Loom 把这些概念变成界面功能：

- 用户不用知道 memory 文件在哪里。
- 用户不用手动复制 compact 摘要。
- 用户不用猜测当前项目是否有上下文。
- 用户不用通过日志判断是否压缩。
- 用户不用自己统计 token。

这对产品经理、运营、设计、内容团队、教育行业、咨询行业等用户更友好。

### 17.3 更强的项目边界

CLI 通常以目录为主要边界。

Loom 在目录基础上增加了产品层的项目概念。

Loom 项目可以包含：

- 项目说明。
- 项目 session。
- 项目统计。
- 项目 memory。
- 项目 tasks。
- 项目 skills。
- 项目附件。
- 项目模板。

这让上下文从“一个目录”升级为“一个可持续经营的工作空间”。

### 17.4 更强的记忆治理

CLI 中的记忆更偏文件管理。

用户需要自己知道写在哪里、怎么写、什么时候生效。

Loom 增加了记忆治理流程：

- L0 事实记录。
- L1 近期观察。
- L2 语义记忆和项目规则。
- L3 项目档案。
- 三道闸门。
- 低 token 批处理晋升。
- 去重。
- 衰减、过期和 negative prior。
- 右侧面板只展示项目理解和待处理事项。
- 后续可审计。

这更适合长期使用。

### 17.5 更强的压缩体验

CLI 中执行 compact 后，用户通常只能看到命令结果。

Loom 把 compact 变成一个明确的界面事件：

- 有压缩动画。
- 有完成状态。
- 有分割线。
- 有摘要。
- 有上下文边界。
- 有后续继续状态。

这对长任务很重要，因为用户需要知道“上下文从哪里开始被整理过”。

### 17.6 更强的附件治理

CLI 更适合文本和文件路径。

Loom 更适合用户直接上传附件。

因此 Loom 需要额外处理：

- 图片。
- PDF。
- 截图。
- 长文档。
- 超大附件提醒。
- 附件预览。
- 附件上下文控制。

这对桌面端用户更自然。

### 17.7 更强的教学属性

Loom 不只是执行工具，也是一个帮助用户理解 AI 工作方式的产品。

通过 token、memory、compact、prompt 结构预览等功能，用户会逐步理解：

- 为什么 AI 有时会忘。
- 为什么长对话需要压缩。
- 为什么记忆要确认。
- 为什么附件不能无限上传。
- 为什么项目边界很重要。

这符合 Loom 作为“肩负教学属性的 Agent 桌面 App”的定位。

## 18. 用户典型流程

### 18.1 新项目第一次使用

```text
用户进入项目
  ↓
看到项目统计页面
  ↓
直接在底部输入任务
  ↓
Loom 自动创建第一个 session
  ↓
AI 开始回答
  ↓
回复完成后显示 token 用量
  ↓
如产生有价值信号，进入 L1 观察或待处理事项
```

用户不需要先理解 session、memory、compact 等概念。

### 18.2 长对话继续推进

```text
用户持续多轮对话
  ↓
上下文逐渐变长
  ↓
Loom 显示每轮 token 和上下文状态
  ↓
用户或系统触发 compact
  ↓
聊天流中出现压缩分割线
  ↓
展示压缩摘要
  ↓
用户继续对话
```

用户的感受应该是：长任务没有断，只是被整理了一次。

### 18.3 记住项目规则

```text
用户说出项目规则
  ↓
AI 回复完成
  ↓
Loom 记录 L0 fact 并生成 L1 观察
  ↓
低风险规则进入 shadow 观察
  ↓
高影响或冲突规则进入需要处理区
  ↓
重复证据强化为 L2 项目规则
  ↓
后续 session 自动受该规则影响
```

### 18.4 用户明确要求记住

```text
用户说“请记住……”
  ↓
Loom 识别这是记忆意图
  ↓
提取真正需要保存的内容
  ↓
高置信低风险内容进入 L1/L2，边界内容进入需要处理区
  ↓
后续按固定预算注入
```

关键点是：Loom 要记住具体内容，而不是机械记住“请记住上面的内容”这句话。

### 18.5 上传大附件

```text
用户上传附件
  ↓
Loom 检查文件大小
  ↓
超过 20MB 时提示
  ↓
用户选择更小文件、摘要或按需处理
  ↓
AI 使用合适的附件上下文回答
```

目标是避免大附件直接破坏上下文质量。

### 18.6 工具输出过长

```text
AI 调用工具
  ↓
工具返回大量内容
  ↓
Loom 在界面保留可查看信息
  ↓
后续上下文只保留关键摘要
  ↓
AI 继续任务
```

用户能看到执行结果，但后续对话不会被超长输出拖垮。

## 19. 用户界面中的关键位置

### 19.1 聊天消息底部

展示：

- AI 回复耗时。
- 输入 token。
- 输出 token。
- 其他必要状态。

这是用户最常看到上下文消耗的位置。

### 19.2 输入 Token 悬浮层

展示“输入Token组成分类”。

用于解释输入 token 来自哪些类型的上下文。

### 19.3 聊天流中的压缩分割线

展示 compact 发生的位置。

用户可以一眼看到上下文从哪里被整理过。

### 19.4 右侧 Memory 面板

展示：

- 自动进化概览。
- L3 Project Dossier。
- L2 Semantic Memories。
- L1 Recent Observations。
- 需要处理的高影响事项。
- 注入预览。

这是用户理解“Loom 当前如何理解项目”的主要入口。

它不是文件浏览器，也不是审计日志面板。

### 19.5 右侧 Tasks 面板

展示任务状态。

当 AI 本轮涉及任务更新时，可以自动切换到 Tasks。

### 19.6 项目统计页

当项目没有 session 时，默认展示项目统计页。

用户仍然可以直接输入第一条消息，不需要先创建 session。

### 19.7 设置页

设置页适合放：

- 自动压缩开关。
- 上下文显示偏好。
- Memory / Evolution 自动记录与晋升策略。
- 大附件提醒策略。
- 高级 Prompt 结构预览开关。

普通用户不需要频繁调整这些设置。

## 20. 当前版本已经形成的能力闭环

Loom CC 现在的上下文管理已经形成以下闭环。

### 20.1 长对话闭环

```text
持续聊天
  ↓
上下文增长
  ↓
显示 token 和上下文状态
  ↓
触发 compact
  ↓
显示压缩边界和摘要
  ↓
继续聊天
```

### 20.2 记忆闭环

```text
对话产生重要信息
  ↓
L0 事实记录
  ↓
cheap gate 判断价值和置信度
  ↓
L1 近期观察
  ↓
批量晋升 / 去重 / 衰减
  ↓
L2 语义记忆或项目规则
  ↓
L3 项目档案
  ↓
按固定预算注入后续 session
  ↓
用户只处理高影响、冲突或低置信事项
```

### 20.3 项目闭环

```text
进入项目
  ↓
查看项目状态
  ↓
开始或继续 session
  ↓
产生任务、记忆、文件和反馈
  ↓
沉淀到项目上下文
  ↓
下次进入项目继续使用
```

### 20.4 附件闭环

```text
上传附件
  ↓
检查大小和类型
  ↓
小文件直接使用
  ↓
大文件提醒或摘要
  ↓
AI 基于合适内容回答
```

### 20.5 工具结果闭环

```text
AI 调用工具
  ↓
展示执行结果
  ↓
长结果进行瘦身
  ↓
后续只保留关键信息
  ↓
继续任务
```

## 21. 当前边界和用户预期

### 21.1 Loom 不应该承诺“永远不丢上下文”

任何 AI 工具都有上下文窗口限制。

Loom 的目标不是突破物理限制，而是让限制更可见、更可控、更不容易突然影响用户。

### 21.2 Loom 不应该把所有观察都升级为长期记忆

自动保存和自动晋升全部信息会带来风险：

- 记错。
- 重复。
- 过时。
- 项目之间互相污染。
- 隐私泄露。

所以 Loom 的策略不是“全部自动保存”，也不是“全部交给用户确认”，而是分层处理：

- L0 可以确定性留痕。
- L1 可以低成本记录近期观察。
- L2 必须经过重复证据、去重和置信过滤。
- 高影响或冲突事项才需要用户确认。
- 用户否决过的方向会进入 negative prior，避免反复出现。

### 21.3 Loom 不应该把所有附件都完整发给 AI

完整发送大附件会带来：

- 成本高。
- 速度慢。
- 易失败。
- 上下文被撑爆。
- 重点不清晰。

所以大附件需要提醒、摘要或按需引用。

### 21.4 Loom 不应该依赖不准确的发送前估算

发送前 token 估算可能与真实情况差别较大。

Loom 更应该展示回复完成后的真实用量，并根据真实数据做后续管理。

## 22. 后续优化方向

### 22.1 更好的项目上下文健康面板

项目可以有一个上下文健康面板。

展示：

- 长对话数量。
- 最近 compact 时间。
- 需要处理事项数量。
- 大附件数量。
- 工具长输出次数。
- 项目 memory 规模。
- L2 stale 数量。
- 被 negative prior 拦截的候选数量。

### 22.2 更好的大附件索引

未来大附件不应该只是“拒绝”或“截断”。

更好的方式是：

- 建立索引。
- 先生成目录。
- 用户选择关注范围。
- AI 按需检索片段。

### 22.3 更好的压缩质量展示

压缩后可以展示：

- 压缩前后 token 变化。
- 保留了哪些任务。
- 保留了哪些决策。
- 舍弃了哪些低价值内容。

### 22.4 更好的上下文时间线

将 session 中的重要事件变成时间线：

- 创建 session。
- 上传附件。
- 产生任务。
- 生成记忆候选。
- 确认记忆。
- 执行 compact。
- 工具执行失败。
- 上下文状态变化。
- L1 观察晋升为 L2。
- L2 规律 stale 或归档。

这会让复杂项目更容易复盘。

### 22.5 更好的 skill 搭车产出

Memory 候选不应该总是由独立 memory extractor 生成。

更好的方式是：

- 主任务 skill 在已有 LLM 调用中顺带输出 memory candidates。
- `memory-curator` 只处理批量或模糊 case。
- `rule-promoter` 只处理具备长期规则潜力的 decision / retrospective。
- `token-economist` 定期评估哪些 memory/rule 值得注入。

这样 memory/evolution 能力会随着 skill 体系增强，但不会显著增加每轮对话成本。

## 23. 一句话总结

Loom CC 的上下文管理不是简单地把更多内容塞给 AI，而是把“会话历史、项目资料、长期记忆、附件、工具结果和压缩摘要”组织成一个用户可见、可控、可持续的工作系统。

相比 CLI，Loom 的核心优势不是底层能力更多，而是把上下文管理产品化：用户能看见、能确认、能压缩、能复盘，也能在更长周期的项目中持续使用 AI。
